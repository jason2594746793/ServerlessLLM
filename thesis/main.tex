\title{Efficient Scheduling for Batched AI Jobs: Minimising Makespan through Model Grouping, Johnson's Rule, and Checkpoint Prefetching}

\author{Jingsheng}

\course{Computer Science}

\project{4th Year Project Report}

\date{March 2026}

\abstract{
Large Language Model (LLM) batch workloads---encompassing model benchmarking, dataset labelling, and synthetic data generation---submit hundreds of tasks that share common model weights. Existing serverless LLM schedulers treat tasks as independent, causing excessive model switching that dominates total execution time.

This dissertation formalises the batch scheduling problem as a two-machine flow-shop (I/O and GPU computation) and introduces three composable optimisations: (1)~\textbf{model grouping} reduces model switches from $O(n)$ to $O(k)$; (2)~\textbf{Johnson's Rule ordering} sequences model groups to maximise I/O-computation overlap; and (3)~\textbf{checkpoint prefetching} preloads the weights of the next model into CPU pinned memory while the current group executes.

Evaluation on NVIDIA RTX A5000 GPUs shows that model grouping reduces makespan by 99\% over FIFO (78,900s to 1,107s for a 500-task batch with five models). Checkpoint prefetching hides 68.7\% of model loading latency. Johnson's Rule provides 7.2--22.0\% additional makespan reduction over naive orderings. The shared-aware strategy outperforms FIFO by 49--237$\times$ across batch sizes of 100--10,000 tasks and model sizes of 0.6B--32B, with advantages growing as batch size increases. Prefetching remains effective across storage tiers including 10\,GbE network storage (78.9\% of I/O latency hidden), demonstrating the viability of remote storage in production deployments.
}

\chapter{Introduction}

The emergence of Large Language Models (LLMs) has created substantial demand for batch inference workloads. Unlike online serving, where individual requests require low-latency responses, batch workloads submit thousands of tasks together for offline processing. Common scenarios include:

\begin{itemize}
\item \textbf{Model Benchmarking}: Evaluating multiple candidate models on the same prompt set (e.g., MMLU, HumanEval, MT-Bench) to generate scoring matrices.
\item \textbf{Dataset Processing}: Using a single model to label, translate, or summarise large corpora for downstream training.
\item \textbf{Synthetic Data Generation}: Creating training data by applying the same model and prompt template to numerous data points.
\end{itemize}

These batch workloads exhibit a critical property that existing schedulers overlook: \textit{tasks within a batch are not independent}. They share substantial computational structure---identical model weights and common prompt prefixes---that can be exploited to reduce total execution time.

\section{Motivation}

Consider a model benchmarking scenario: evaluating two LLMs on 10 questions each, totalling 20 tasks. A naive scheduler executes tasks in submission order (ABABAB\ldots), repeatedly loading and evicting model weights. Since each model switch takes on the order of 100 seconds while each inference requires under a second, the system spends over 96\% of its time on I/O. Grouping tasks by model (AAAA\ldots BBBB) reduces switches from 10 to~1, cutting execution time by 87\% (Figure~\ref{fig:fifo_vs_grouped}).

The key observation is that \textit{batch tasks contain exploitable shared structure, and the scheduler should discover and leverage this structure to minimise makespan}. Reducing model switches from $O(n)$ to $O(k)$ through grouping provides an order-of-magnitude improvement.

However, grouping alone does not eliminate the remaining $O(k)$ model transitions. \textbf{Checkpoint prefetching} hides this residual latency by loading the weights of the next model into CPU pinned memory while the current group executes on GPU. Since I/O and GPU computation use independent hardware resources, they can proceed in parallel.

Prefetching effectiveness depends on the \textit{order} in which groups execute: a group with long compute time provides a large overlap window, while a short group provides little. This structure---in which each model group passes through two sequential stages (I/O loading then GPU computation), with the objective of minimising total completion time---is precisely the classical \textit{two-machine flow-shop} problem~\cite{johnson1954optimal}. Johnson's Rule provides the provably optimal group ordering by placing compute-heavy groups first, maximising the overlap window for prefetching.

The three components compose into a complete pipeline: grouping reduces switches from $O(n)$ to $O(k)$, prefetching hides I/O behind computation, and Johnson's Rule maximises overlap. Despite this opportunity, existing serverless LLM schedulers treat batch tasks as independent, resulting in excessive model switching and no I/O-computation overlap.

\section{Problem Definition}

\textbf{Concrete batch structure.}
A batch is submitted as a JSONL file in which each line specifies one task: the target model, the prompt, and generation parameters. The example below shows a small multi-model batch typical of the model benchmarking scenario described above.

\begin{lstlisting}[language={},basicstyle=\ttfamily\small,frame=single,numbers=none]
{"custom_id":"t1","method":"POST","url":"/v1/chat/completions",
 "body":{"model":"Qwen/Qwen3-0.6B",
         "messages":[{"role":"user","content":"Summarise the paper."}],
         "max_tokens":256}}
{"custom_id":"t2","method":"POST","url":"/v1/chat/completions",
 "body":{"model":"Qwen/Qwen3-8B",
         "messages":[{"role":"user","content":"Summarise the paper."}],
         "max_tokens":256}}
{"custom_id":"t3","method":"POST","url":"/v1/chat/completions",
 "body":{"model":"Qwen/Qwen3-0.6B",
         "messages":[{"role":"user","content":"Translate to French."}],
         "max_tokens":128}}
\end{lstlisting}

Tasks \texttt{t1} and \texttt{t3} target the same model and therefore share its weights; a scheduler that recognises this can execute them consecutively without reloading. Task \texttt{t2} targets a different model, requiring a model switch. The batch API follows the OpenAI Batch API specification \citep{openai_batch_api}: clients submit a file via \texttt{POST /v1/files}, create a batch job via \texttt{POST /v1/batches}, and poll for results via \texttt{GET /v1/batches/\{id\}}. Results are written to an output JSONL file with one response per line, keyed by \texttt{custom\_id}.

We formalise the batch scheduling problem as follows:

\textbf{Input:}
\begin{itemize}
\item A batch of $n$ tasks $B = \{t_1, t_2, \ldots, t_n\}$
\item Each task $t_i = (m_i, p_i, \theta_i)$ where $m_i$ is the model, $p_i$ is the prompt, and $\theta_i$ are generation parameters
\item A cluster of $k$ GPU workers $W = \{w_1, w_2, \ldots, w_k\}$
\item Each worker can load at most one model at a time, with loading latency $L_{load}(m)$
\item Task inference latency is $L_{infer}(t_i)$
\end{itemize}

\textbf{Sharing Relationships:}
\begin{itemize}
\item \textbf{Model Sharing}: If $m_i = m_j$, tasks $t_i$ and $t_j$ can share loaded model weights, avoiding redundant loading. This is the primary sharing relationship exploited in this work.
\item \textbf{Prefix Sharing}: If $\text{prefix}(p_i) = \text{prefix}(p_j)$, tasks can benefit from inference engine cache reuse. This is a secondary sharing relationship identified but not exploited in this work (see Chapter~\ref{ch:future}).
\end{itemize}

\textbf{Optimisation Objective:}
$$\text{Minimise } C_{max} = \max_{i \in \{1,...,n\}} \text{completion\_time}(t_i)$$

That is, minimise the \textit{makespan}---the time at which the last task completes.

\textbf{Constraints:}
\begin{itemize}
\item Each worker loads at most one model at a time (single-model constraint)
\item Model switching incurs $L_{load}$ overhead (cold start penalty)
\item Worker count $k$ can be adjusted via auto-scaling
\end{itemize}

\section{Research Questions}

This dissertation addresses three research questions:

\begin{description}
\item[RQ1:] How can we discover shared structure (shared models) in a batch of tasks and exploit it to reduce makespan? Specifically, how does model grouping compare to naive FIFO scheduling?

\item[RQ2:] Can the batch scheduling problem be modelled as a two-machine flow-shop (I/O and compute), and does Johnson's Rule provide an effective ordering of model groups to maximise I/O-computation overlap via checkpoint prefetching?

\item[RQ3:] How do different scheduling strategies (FIFO, Model Grouping, Shared-Aware with prefetching) compare across varying batch sizes, model sizes, and storage tiers (local SSD, RAID, network storage)?
\end{description}

\section{Contributions}

This work makes the following contributions:

\begin{enumerate}
\item \textbf{Two-Machine Flow-Shop Formulation}: The batch scheduling problem is modelled as a classical two-machine flow-shop where Machine~A is I/O (loading model weights) and Machine~B is GPU computation, enabling the application of Johnson's Rule for provably optimal model group ordering.

\item \textbf{Shared-Aware Scheduling Algorithm}: An algorithm that discovers model sharing relationships within a batch, groups tasks by model to reduce switches from $O(n)$ to $O(k)$, and applies Johnson's Rule to order groups for maximal I/O-computation overlap.

\item \textbf{Checkpoint Prefetching Mechanism}: A prefetching policy that leverages the pinned memory pool of ServerlessLLM to preload the weights of the next model while the current group executes, hiding I/O latency through pipelining.

\item \textbf{Network-Aware Prefetching Extension}: Analysis and evaluation of prefetching across storage tiers including RAID-0, 10\,GbE NFS, and 100\,GbE NFS, demonstrating that the prefetch architecture generalises to network-attached storage.

\item \textbf{OpenAI-Compatible Batch API}: An OpenAI-compatible batch REST API extended for multi-model batches, enabling clients to submit heterogeneous task lists with a single request and receive results asynchronously.
\end{enumerate}

In total, this project contributed approximately 3,500 lines of new Python code to the existing ServerlessLLM framework ($\sim$15K LoC).

\section{Scope and Boundaries}

This work focuses strictly on \textit{cluster-level scheduling}. The inference engine itself is neither modified nor optimised. Specifically, this work does not address:

\begin{itemize}
\item KV cache management within the inference engine (e.g., PagedAttention, block allocation)
\item Prefill-decode separation or continuous batching internals
\item GPU kernel optimisations or quantization techniques
\end{itemize}

The scheduler operates at a higher abstraction level, deciding \textit{which tasks to execute, in what order, and on which workers}. The inference engine (vLLM) handles the actual computation. This separation of concerns is deliberate---scheduler-level optimisations are complementary to engine-level optimisations and can be applied without modifying the inference engine.

\chapter{Background}

This chapter introduces the technical foundations required to understand the shared-aware scheduling system. Topics covered include the transformer architecture and its inference characteristics, the KV cache mechanism and prefix caching, the GPU memory hierarchy and pinned memory transfers, serverless computing and the cold start problem, the storage hierarchy (local SSD, RAID, and network-attached storage), and the ServerlessLLM framework that this work extends.

\section{Transformer-Based LLM Inference}

Large Language Models are built on the transformer architecture \citep{vaswani2017attention}, which generates output tokens autoregressively. Inference consists of a compute-bound \textit{prefill phase} ($O(L^2)$ attention over the input prompt) followed by a memory-bandwidth-bound \textit{decode phase} (one token per step, each pass reading the full model weights). Modern LLMs range from 0.5B to 405B parameters \citep{brown2020language, touvron2023llama}; an 8B model requires $\sim$15\,GB in FP16 precision, while a 70B model requires $\sim$140\,GB---exceeding the memory capacity of a single GPU. Loading these weights from storage to GPU memory constitutes a major bottleneck, taking 80--120 seconds for an 8B model from SSD.

\textbf{Continuous batching.} To improve GPU utilisation, vLLM \citep{kwon2023efficient} introduced \textit{continuous batching} (also called iteration-level scheduling): rather than waiting for an entire request batch to finish before admitting new requests, the inference engine inserts new requests into the batch at every decode step as slots become free. This maintains near-full GPU utilisation during single-model serving. However, continuous batching operates \textit{within} a single loaded model; it does not address the problem of switching between models in a multi-model batch.

\textbf{Tensor parallelism.} When a model's weights exceed a single GPU's VRAM, \textit{tensor parallelism} \citep{shoeybi2019megatron} shards weight matrices across multiple GPUs, with each GPU computing a slice of each matrix multiplication and exchanging activations via all-reduce. This enables inference on 70B+ models using multiple GPUs. This work assumes each model fits within a single GPU's VRAM; tensor parallelism is an orthogonal technique that could be combined with the proposed scheduler when models span multiple GPUs.

\section{KV Cache and Prefix Caching}
\label{sec:bg_kv_cache}

During autoregressive generation, inference engines cache key and value tensors (the \textit{KV cache}) to avoid redundant computation. vLLM \citep{kwon2023efficient} manages the KV cache in fixed-size blocks via \textit{PagedAttention}, eliminating fragmentation. When multiple requests share a common prompt prefix, the KV blocks can be computed once and reused \citep{zheng2024sglang}. However, cache effectiveness depends on task ordering: interleaving different prefixes causes eviction. This prefix-level optimisation is complementary to the model grouping approach proposed in this work but is not directly exploited here (see Chapter~\ref{ch:future}).

\section{GPU Memory Hierarchy and Pinned Memory}
\label{sec:bg_pinned_memory}

Loading model weights from storage to GPU involves a multi-level memory hierarchy:

\begin{enumerate}
\item \textbf{Disk/SSD} $\rightarrow$ \textbf{CPU memory} (host RAM): Read checkpoint files via filesystem I/O. Bandwidth: 2--5\,GB/s (NVMe SSD).
\item \textbf{CPU memory} $\rightarrow$ \textbf{GPU memory} (VRAM): Transfer via PCIe DMA. Bandwidth: 16--32\,GB/s (PCIe Gen4 x16).
\end{enumerate}

The CPU$\rightarrow$GPU transfer step is significantly faster when using \textit{pinned memory} (also called page-locked memory). Regular (pageable) memory may be swapped to disk by the OS, necessitating an extra copy to a pinned staging buffer before DMA transfer. Pinned memory, allocated via \texttt{cudaHostAlloc} or registered via \texttt{cudaHostRegister} \citep{cuda_guide2024}, is guaranteed to remain in physical RAM, enabling direct DMA transfers without intermediate copies.

The sllm-store component of ServerlessLLM \citep{fu2024serverlessllm} exploits this by pre-allocating a pinned memory pool at startup. Model weights are loaded from SSD directly into this pool using multi-threaded I/O, then transferred to the GPU via DMA. This two-stage pipeline (SSD$\rightarrow$pinned CPU$\rightarrow$GPU) achieves near-peak PCIe bandwidth, reducing model loading time relative to a direct \texttt{torch.load()} call, which relies on pageable memory.

\section{Serverless Computing and Cold Starts}

Serverless functions suffer from \textit{cold starts}: the latency incurred when initialising a new instance \citep{shahrad2020serverless}. For LLM inference, cold starts are particularly severe---loading model weights takes 80--120\,s for an 8B model, which is 100--200$\times$ the per-request inference latency ($\sim$0.5\,s). ServerlessLLM \citep{fu2024serverlessllm} mitigates this through locality-enhanced scheduling that routes inference to nodes with locally cached checkpoints.

\section{ServerlessLLM Architecture}
\label{sec:bg_serverlessllm}

ServerlessLLM \citep{fu2024serverlessllm} is an open-source serverless LLM inference framework designed for low-latency model loading. Its architecture consists of four components:

\begin{itemize}
\item \textbf{Head Node}: Receives inference requests via an API gateway, maintains deployment state in a SQLite database, and dispatches tasks to workers via a Router.
\item \textbf{Workers (Pylets)}: GPU nodes managed by the Pylet process manager. Each worker runs vLLM \citep{kwon2023efficient} instances for inference. Pylet handles instance lifecycle (start, stop, health checks) and reports resource availability.
\item \textbf{sllm-store}: A C++ storage daemon running on each worker that manages a pinned memory pool and provides gRPC endpoints for model loading. Key operations include \texttt{LoadModelAsync} (load weights into pinned CPU memory) and \texttt{RegisterModel} (register a model path). sllm-store uses multi-threaded I/O to saturate SSD bandwidth during loading \citep{grpc2024}.
\item \textbf{AutoScaler}: Monitors deployment state and adjusts the number of vLLM instances based on demand. The default policy is reactive: scale up when queue depth exceeds a threshold, scale down after an idle timeout.
\end{itemize}

The current scheduler of ServerlessLLM is designed for online serving: it assigns incoming requests to available workers using round-robin. For batch workloads, this approach has two limitations: (1) tasks are assigned independently without considering shared models or prefixes, leading to excessive model switching; and (2) scaling is reactive rather than proactive, causing unnecessary cold starts at the beginning of a batch.

\section{Storage Hierarchy and Network-Attached Model Repositories}
\label{sec:bg_storage_hierarchy}

The choice of storage tier directly affects the batch scheduling problem: it determines the I/O time $a_i$ in the two-machine flow-shop formulation (Section~\ref{sec:bg_johnsons_rule}), and thus the effectiveness of checkpoint prefetching.

Local NVMe SSDs provide 2--5\,GB/s sequential read; RAID-0 (4$\times$) aggregates to 8--12\,GB/s. Remote storage --- object storage (S3, GCS) or network file systems (NFS, Lustre) --- provides unlimited capacity and built-in replication, with bandwidth ranging from 1.2\,GB/s (10\,GbE) to 12\,GB/s (100\,GbE). Production systems use local SSD as a cache and remote storage as the source of truth. The scheduling implications of different storage tiers are analysed in Section~\ref{sec:prefetch_storage_tiers}.

\section{Makespan Minimisation}
\label{sec:bg_makespan}

Makespan minimisation --- assigning $n$ jobs to $m$ machines to minimise the completion time of the last job, $C_{\max}$ \citep{pinedo2016scheduling} --- is a classical scheduling problem. The Longest Processing Time (LPT) rule \citep{graham1966bounds} provides a $(4/3 - 1/(3m))$-approximation for identical machines. LLM batch scheduling differs because jobs have sequence-dependent setup times (model loading: $\sim$100\,s for switches, zero for same-model jobs), making the problem NP-hard in general \citep{pinedo2016scheduling}.

\subsection{Johnson's Rule for Two-Machine Flow-Shops}
\label{sec:bg_johnsons_rule}

Johnson's Rule \citep{pinedo2016scheduling} provides the optimal solution for the two-machine flow-shop problem: given $n$ jobs that must be processed first on Machine~A then on Machine~B, find the permutation that minimises makespan. The algorithm partitions jobs into two sets:

\begin{itemize}
\item $S_1 = \{j : a_j \leq b_j\}$ --- jobs where Machine~A time is at most Machine~B time. Sort $S_1$ by $a_j$ in ascending order.
\item $S_2 = \{j : a_j > b_j\}$ --- jobs where Machine~A time exceeds Machine~B time. Sort $S_2$ by $b_j$ in descending order.
\end{itemize}

The optimal sequence is $S_1$ followed by $S_2$. The intuition is that compute-heavy jobs ($a_j \leq b_j$) should execute first: their prolonged execution on Machine~B conceals the loading of the subsequent job on Machine~A. I/O-heavy jobs ($a_j > b_j$) should be scheduled last, since fewer subsequent jobs remain to stall while their loading completes.

This is directly applicable to the problem at hand: Machine~A is the I/O stage (loading model weights from SSD to CPU pinned memory), Machine~B is the compute stage (GPU inference for all tasks in a model group), and each job is a model group. This mapping is formalised in Chapter~4.

\chapter{Related Work}

This chapter positions the proposed work relative to existing systems and techniques. We examine LLM batch workloads, ML serving systems, data-locality-aware scheduling, and prefetching mechanisms, identifying the gap that the shared-aware scheduler addresses.

\section{LLM Batch Workloads}

LLM inference is increasingly used for batch workloads rather than interactive serving. Three common patterns drive this trend:

\textbf{Model benchmarking.} Evaluating candidate models on standardised test suites (MMLU \citep{hendrycks2020measuring}, HumanEval \citep{chen2021evaluating}, MT-Bench \citep{zheng2023judging}) requires running the same prompt set across different models. Comparing five models on 1,000 prompts yields 5,000 tasks with high prompt overlap but diverse model identities.

\textbf{Dataset processing.} Large-scale labelling, translation, or summarisation applies a single model to large corpora. All tasks share the model but have different inputs.

\textbf{Synthetic data generation.} Training data generation uses template-based prompts with variable data points, exhibiting both model and prompt template overlap.

Industrial systems recognise this trend. The OpenAI Batch API \citep{openai_batch_api} supports up to 50,000 tasks per batch with 50\% cost savings. AWS Bedrock Batch \citep{aws_bedrock_batch} provides similar functionality. However, both are closed-source, support only single-model batches, and do not expose scheduling policies.

\section{ML Serving Systems}

Several systems address the challenge of serving ML models at scale:

\textbf{Clipper} \citep{crankshaw2017clipper} provides a prediction serving system with model containers, adaptive batching, and model selection policies. It focuses on latency SLOs for online serving rather than batch throughput.

\textbf{INFaaS} \citep{romero2021infaas} automates model variant selection (different precisions, batch sizes) to meet latency and cost objectives. It treats model switching as a configuration change rather than a bottleneck.

\textbf{Clockwork} \citep{gujarati2020serving} achieves predictable DNN serving latency through precise profiling and centralised scheduling. Its key insight --- that DNN inference times are highly predictable --- does not extend to autoregressive LLM generation where output length varies.

\textbf{AlpaServe} \citep{li2023alpaserve} uses statistical multiplexing with model parallelism to serve multiple models on shared GPU clusters. It addresses the model placement problem but does not consider batch-level task reordering.

\textbf{vLLM} \citep{kwon2023efficient} is the de facto standard LLM serving system. It combines PagedAttention (non-contiguous KV cache) with continuous batching and a high-throughput scheduler. vLLM also supports tensor parallelism for multi-GPU inference of large models. Crucially, vLLM is designed for \textit{single-model} serving: it assumes all requests share one loaded model and optimises GPU utilisation within that constraint. In multi-model batch scenarios, unmodified use of vLLM would still require sequential model loads between groups---the problem that this scheduler addresses.

\textbf{Orca} \citep{yu2022orca} introduced iteration-level scheduling for transformer serving, enabling continuous batching where new requests join an in-progress batch at each decode step. This is complementary to the present work: Orca and vLLM optimise \textit{within-model} batching, while this work optimises \textit{across-model} task ordering at the cluster scheduler level.

None of these systems address the specific problem of batch-level shared-structure discovery and exploitation for makespan minimisation.

\section{Data-Locality and Model-Aware Scheduling}

The principle of moving computation to data rather than data to computation is well-established:

\textbf{Data locality in distributed computing.} MapReduce \citep{dean2008mapreduce} and Spark \citep{zaharia2010spark} schedule tasks on nodes that hold the input data, minimising network transfer. For LLM inference, the analogous principle is scheduling tasks on nodes that hold the model weights.

\textbf{Cluster resource management.} Google's Borg \citep{verma2015large} and Kubernetes \citep{kubernetes2024} provide general-purpose cluster scheduling with affinity rules and resource constraints. Dominant Resource Fairness \citep{ghodsi2011dominant} addresses multi-resource allocation. These systems provide scheduling infrastructure but do not implement application-specific optimisations such as model grouping.

\textbf{Shared computation discovery.} Database query optimisers perform multi-query optimisation to identify common subexpressions across queries \citep{sellis1988multiple}. This inspires the present approach: analyse the batch to discover shared structure (models, prefixes), then optimise execution order.

\textbf{ServerlessLLM} \citep{fu2024serverlessllm} provides locality-enhanced scheduling that caches checkpoints on local SSDs. However, the scheduler is reactive and does not reorder batch tasks by model or prefix.

\section{Prefetching and Pipelining}

Prefetching hides I/O latency by loading data before it is needed:

\textbf{OS-level prefetching.} Virtual memory systems prefetch pages based on sequential or strided access patterns \citep{patterson2013computer}. The key requirement is predictability of future accesses.

\textbf{Engine-level prefetching.} DeepSpeed-Inference \citep{aminabadi2022deepspeed} prefetches transformer layers during inference, overlapping CPU$\rightarrow$GPU transfer with computation. FlexGen \citep{sheng2023flexgen} pipelines model offloading across CPU, GPU, and disk for memory-constrained inference. These operate within the inference engine at layer granularity.

\textbf{Checkpoint management.} CheckFreq \citep{mohan2021checkfreq} optimises DNN checkpoint frequency during training, balancing overhead against recovery time. While focused on training, its analysis of checkpoint I/O costs is relevant to our model loading analysis.

\textbf{Gap: cluster-level prefetching.} To our knowledge, no existing system performs checkpoint prefetching at the cluster scheduler level. Existing prefetching is either OS-level (page prefetching) or engine-level (layer prefetching). This work introduces \textit{task-group-level prefetching}: the scheduler predicts which model will be needed next based on the execution plan and begins loading it before the current task group completes.

\chapter{Design and Implementation}

This chapter presents the design of the shared-aware scheduling system, focusing on four key components: (1) shared-structure analysis that discovers model sharing relationships in batch tasks; (2) a two-machine flow-shop formulation to which Johnson's Rule is applied, optimally ordering model groups for I/O-computation overlap; (3) checkpoint prefetching that hides model loading latency; and (4) multi-GPU load balancing that distributes model groups across available workers.

\section{System Architecture Overview}

The system extends the head node of ServerlessLLM with three new components: the \textbf{BatchScheduler} (model grouping and Johnson's Rule ordering), the \textbf{StorageManager} (checkpoint prefetching into the pinned memory pool of sllm-store), and a batch-aware \textbf{AutoScaler} integration. These operate at the cluster scheduler level without modifying the inference engine. A \textbf{SQLite database} (\texttt{state.db}) on the head node serves as the shared state store: the BatchScheduler persists batch jobs, task status, and deployment configuration; the Router reads healthy worker endpoints from the same database to route requests. The data flow proceeds as follows: (1)~the user submits a batch via the API Gateway; (2)~the BatchScheduler groups tasks by model, applies Johnson's Rule, persists job state to the database, and feeds ordered tasks to the Router; (3)~the Router queries the database for healthy endpoints and dispatches tasks to vLLM workers; (4)~the StorageManager prefetches the weights of the next model while the current group executes; (5)~the AutoScaler adjusts instance count based on batch demand.

\section{Problem Analysis: Shared Structure in Batches}

\subsection{Model Sharing Analysis}

Batch workloads exhibit substantial model sharing. In model benchmarking scenarios, multiple tasks use the same model with different prompts. In dataset processing, all tasks use a single model. This sharing creates an optimisation opportunity: if tasks using the same model execute consecutively on the same worker, the model weights remain loaded in GPU memory, avoiding redundant loading.

Consider a batch with $n$ tasks using $k$ distinct models. If tasks are executed in arbitrary order (e.g., ABABABAB for two models), the system incurs $O(n)$ model switches in the worst case. Each switch requires evicting the current model weights (15\,GB for an 8B parameter model) and loading the new model from storage, taking 80--120 seconds depending on storage bandwidth.

In contrast, grouping tasks by model (AAAA\ldots BBBB) reduces switches to $O(k)$---one per model transition. For a batch with 20 tasks alternating between two models, grouping reduces switches from 10 to 1, eliminating $9 \times 108 = 972$ seconds of overhead.

The key insight is that model loading latency $L_{load}$ is typically 100--200$\times$ larger than per-task inference latency $L_{infer}$ (80--120s vs 0.5--1s). Minimising model switches therefore has first-order impact on makespan, while optimising inference latency has only second-order impact.

\subsection{Prefix Sharing Analysis}

Beyond model sharing, batch tasks often share common prompt prefixes (e.g., RAG contexts, few-shot examples, system prompts). Modern inference engines support prefix caching, reducing prefill time from $\sim$2\,s to $\sim$0.05\,s for shared prefixes. However, model switching incurs 80--120\,s of overhead compared to $<$2\,s for prefix cache misses, making model grouping the first-order optimisation. Prefix-aware task ordering within model groups is left as future work (Chapter~\ref{ch:future}).

\section{Shared-Aware Scheduling Algorithm}

The scheduling algorithm operates in three phases: model grouping, Johnson's Rule ordering, and worker allocation.

\subsection{Phase 1: Model Grouping}

Given a batch $B = \{t_1, t_2, \ldots, t_n\}$, the first phase groups tasks by model to minimise model switches:

\begin{algorithmic}
\STATE $groups \gets \{\}$
\FOR{$t_i \in B$}
  \STATE $m \gets t_i.model$
  \IF{$m \notin groups$}
    \STATE $groups[m] \gets []$
  \ENDIF
  \STATE $groups[m].\text{append}(t_i)$
\ENDFOR
\end{algorithmic}

This produces $k$ model groups $\{G_1, G_2, \ldots, G_k\}$ where each $G_i$ contains all tasks for one model. Grouping alone reduces model switches from $O(n)$ (worst case with interleaved submission) to $O(k)$.

\subsection{Phase 2: Johnson's Rule Ordering}
\label{sec:johnsons_rule}

The scheduling of model groups maps naturally to a \textit{two-machine flow-shop}: each model group must first be loaded from storage (Machine~A: I/O) and then executed on GPU (Machine~B: compute). When checkpoint prefetching is enabled, loading of the next group can overlap with execution of the current group, creating a pipeline. Johnson's Rule determines the group ordering that minimises makespan under this overlap structure.

For each model group $G_i$, two times are estimated:
\begin{itemize}
\item $a_i$ (I/O time): the time to load model $m_i$'s checkpoint from SSD to CPU pinned memory, estimated as $a_i = \text{checkpoint\_size}(m_i) / \text{NVMe\_bandwidth}$.
\item $b_i$ (compute time): the time to execute all tasks in $G_i$ on GPU, estimated as $b_i = |G_i| \times \tau_{base} \times (\text{model\_size}(m_i) / \text{base\_model\_size})$, where $\tau_{base}$ is the base per-task inference time.
\end{itemize}

The checkpoint size is determined by scanning the model directory for weight files (\texttt{.safetensors}, \texttt{.bin}, \texttt{.pt}), with the result cached after the initial scan.

\STATE $S_1 \gets \{G_i : a_i \leq b_i\}$, sorted by $a_i$ ascending
\STATE $S_2 \gets \{G_i : a_i > b_i\}$, sorted by $b_i$ descending
\STATE $\pi \gets S_1 + S_2$
\end{algorithmic}

\textbf{Why Johnson's Rule outperforms naive ordering.} Consider two model groups with equal total time but different I/O-compute ratios: Group~X with $a=10$s (load) and $b=90$s (compute) is compute-heavy, while Group~Y with $a=90$s (load) and $b=10$s (compute) is I/O-heavy. Under ordering X$\to$Y, the 90s load of Y fully overlaps with X's 90s compute, giving a total of approximately 110s. Under ordering Y$\to$X, only 10s of X's load overlaps with Y's compute, leaving an 80s stall and a total of approximately 190s. Johnson's Rule correctly schedules compute-heavy group X first.

\subsection{Phase 3: Worker Allocation}
\label{sec:worker_allocation}

For multi-GPU deployments, a two-level strategy is employed. At the first level, model groups are sorted by total estimated time ($a_i + b_i$) in descending order and greedily assigned to the GPU with the least total load. When model groups outnumber GPUs, multiple groups share a GPU; when GPUs outnumber groups, the largest group is split between two GPUs, with the receiving GPU paying an additional I/O cost to load the model. An iterative rebalancing step follows: if the slowest GPU's load exceeds the fastest by more than 15\%, tasks are moved from the heaviest group on the slowest GPU to the fastest, continuing until balance is achieved or splitting no longer helps. At the second level, each GPU's queue of model groups is independently ordered using Johnson's Rule, optimising local I/O-computation overlap.

Models that exceed a single GPU's memory (e.g., 32B parameters requiring $\sim$60\,GB) use tensor parallelism (TP), where model weights are sharded across multiple GPUs. The scheduler handles TP models through capacity-aware lane packing: each TP group is assigned to a dedicated execution lane consuming $\textit{tp}$ GPU slots. When GPU budget allows, multiple TP groups run in parallel on non-overlapping GPU subsets---for example, two TP=2 models on 8 GPUs execute simultaneously on separate GPU pairs rather than serialising on a single queue. When budget is insufficient, groups with the same TP size share a lane and execute sequentially. The algorithm processes TP groups in first-fit decreasing order (largest TP first), reserving at least one GPU for single-GPU models when they exist. Single-GPU models are distributed across remaining lanes via greedy LPT with rebalancing, independently of TP lanes. For single-model batches where the model fits on one GPU, the scheduler correctly prefers replicas over TP (4 replicas $\times$ 1 GPU gives 4$\times$ throughput, while TP=4 $\times$ 1 replica gives only $\sim$2$\times$ due to NCCL overhead). The TP size per model is propagated through the deployment's \texttt{backend\_config} to the reconciler, which requests the appropriate number of GPUs from Pylet when creating instances. TP requirements are determined automatically by comparing each model's checkpoint size against available GPU memory: $\text{TP} = 2^{\lceil \log_2 \lceil s_{\text{model}} / (0.8 \cdot m_{\text{GPU}}) \rceil \rceil}$, where $s_{\text{model}}$ is the total weight size and $m_{\text{GPU}}$ is the per-GPU memory. The power-of-two constraint ensures efficient NCCL collective communication. Manual overrides remain available via the API for non-standard configurations.

\subsection{Baseline Strategies}

We compare four scheduling strategies to evaluate the contributions of each optimisation level:

\textbf{FIFO (Baseline).} Tasks are executed in submission order without reordering. This is simple but ignores all shared structure, using synchronous execution.

\textbf{Model Grouping.} Phase~1 only is applied---tasks are grouped by model with alphabetical group ordering and no Johnson's Rule. This isolates the benefit of model grouping from optimal group ordering.

\textbf{Shared-Aware (Proposed).} All three phases are applied---model grouping, Johnson's Rule ordering, and checkpoint prefetching. This is the complete algorithm.

\section{Checkpoint Prefetching Mechanism}

\subsection{Motivation}

Model switching incurs 80--120 seconds of I/O latency to transfer weights from storage to GPU memory. During this interval, the GPU remains idle. If the next required model can be identified and its weights loaded before the current task group completes, I/O and computation can be overlapped, hiding most of the loading latency. The execution plan produced by Johnson's Rule makes this prediction straightforward: the next model group is known from the sequence $\pi$.

\subsection{Prefetching Pipeline}

The prefetching mechanism leverages the sllm-store component of ServerlessLLM \citep{fu2024serverlessllm}, which maintains a pre-allocated pinned memory pool on each worker node (allocated via \texttt{cudaHostAlloc} at startup). When the current model group $G_i$ begins execution, the scheduler immediately triggers prefetching for the model of the next group $G_{i+1}$ by calling \texttt{StorageManager.prefetch\_to\_cpu()}, which issues a gRPC \texttt{LoadModelAsync} request to sllm-store. This loads checkpoint files from local SSD into the pinned memory pool using multi-threaded I/O, making weights DMA-ready for fast GPU transfer.

A \textbf{memory-aware guard} (\texttt{\_can\_prefetch}) checks available CPU pinned memory before triggering prefetch, preventing out-of-memory errors when the pool is occupied by the currently loaded model. If insufficient memory is available, the prefetch is skipped and the model is loaded synchronously at transition time.

\subsection{Design Analysis: Prefetching Across Storage Tiers}
\label{sec:prefetch_storage_tiers}

While the current implementation targets local SSD storage, the prefetching architecture generalises naturally to network-attached storage. This section analyses the design considerations for extending prefetching to remote sources---a critical requirement for production deployments where models are stored in remote object storage (S3, GCS) or network file systems (NFS, Lustre). In the extended design, the storage manager checks the local SSD cache first; on a cache miss, it initiates a background download from the remote repository while the current group executes.

When extended to network-attached storage (S3, NFS), the loading pipeline becomes \textit{Remote Storage $\to$ Local SSD cache $\to$ Pinned CPU Memory $\to$ GPU}. The scheduler estimates download time ($\text{checkpoint\_size} / B_{\text{network}}$) against the current group's compute time and triggers prefetch when overlap is feasible. For slower storage tiers, Johnson's Rule becomes more critical: compute-heavy groups must be scheduled first to provide sufficient overlap windows for network downloads.

If the compute time $b_A$ of the current group is at least as large as the loading time $a_B$ of the next model, the entire loading latency is hidden. Otherwise, the residual $a_B - b_A$ represents unmasked waiting time. For a model with SSD read time $a_i$ and per-task inference time $t$, full prefetch overlap requires at least $\lceil a_i / t \rceil$ tasks in the preceding group. For local SSD, this is easily met for typical task groups; for 10\,GbE network sources, larger groups are needed (see Table~\ref{tab:storage_bandwidth}).

In summary, the shared-aware scheduling algorithm operates at the cluster scheduler level (compatible with any inference engine), applies Johnson's Rule for provably optimal group ordering, and uses checkpoint prefetching with a memory-aware guard to hide model loading latency. The next chapter evaluates these techniques through systematic experiments.

\chapter{Evaluation}

This chapter presents experimental evaluation of the shared-aware scheduling system. We first state four falsifiable hypotheses derived from the design claims, then systematically test each through five experiments.

\paragraph{Hypotheses.}
\begin{description}
\item[H1] \textit{Model grouping dominates.} Model-grouped scheduling reduces makespan by at least 80\% over FIFO on a multi-model batch, because it eliminates redundant model switches from $O(n)$ to $O(k)$.
\item[H2] \textit{Prefetching hides I/O.} Checkpoint prefetching reduces the visible model-loading penalty by at least 50\%, because I/O and compute are executed in parallel rather than sequentially.
\item[H3] \textit{Johnson's Rule beats naive ordering.} Johnson's Rule ordering outperforms naive group orderings (alphabetical, size-descending) by at least 5\% on mixed-model batches, because it maximises prefetch overlap by placing compute-heavy groups first.
\item[H4] \textit{Gains are robust across scale.} The makespan improvements from shared-aware scheduling persist as batch size grows from 100 to 10,000 tasks, confirming that scheduling is not a constant-time overhead.
\end{description}

\subsection{Analysis}

With five models interleaved across 500 tasks, FIFO incurs approximately 499 model switches. The average per-switch overhead across the five model sizes is:
$$\bar{L}_{switch} = \frac{C_{FIFO} - n \cdot \bar{L}_{infer}}{n_{switches}} = \frac{78900 - 500 \times 0.64}{499} \approx 157.2 \text{ s}$$
where $\bar{L}_{infer} = 0.64$s is the per-task average inference time weighted by model size. Model loading accounts for over 99\% of FIFO's total execution time.

Reducing switches from 499 to 4 (one per model boundary), Model Grouping achieves a 71$\times$ speedup (1,107s); the reduction from $O(n)$ to $O(k{-}1) = 4$ switches is the primary driver, since each avoided switch saves approximately 157s of cold loading time. Adding checkpoint prefetching further reduces makespan by 37\% (697s), hiding cold-loading time behind GPU computation even with suboptimal alphabetical group ordering. Johnson's Rule then contributes an additional 21\%: the Shared-Aware strategy (575s) places groups in ascending SSD read time (0.6B $\to$ 4B $\to$ 8B $\to$ 14B $\to$ 32B), ensuring that prefetch windows for the largest model groups are fully utilised.

Hypothesis H1 is therefore confirmed. Model grouping achieves a 99\% makespan reduction over FIFO (78,900s $\to$ 1,107s), far exceeding the 80\% threshold, and the three optimisations are complementary: their combined effect yields a 137$\times$ speedup.

A model-affinity LRU scheduler routes each arriving task to the GPU holding the model weights, evicting the least-recently-used model on a cache miss. This is an online heuristic suited to streaming workloads where tasks arrive continuously and the full task set is unknown. In the offline batch setting all $n=500$ tasks are submitted simultaneously, so the complete task-to-model mapping is known before execution begins. Given full information, any well-informed scheduler performs explicit model grouping as a preprocessing step, making LRU equivalent to Model Grouping and thus not an independent design point. The Model Grouping row in Table~\ref{tab:exp1_results} therefore subsumes model-affinity LRU in the offline batch regime.

\subsection{Analysis}

Checkpoint prefetching reduced makespan by 26.8\% (from 312.4s to 228.7s), saving 83.7 seconds across two model transitions (Figure~\ref{fig:prefetch_timeline}). The average per-transition time dropped from 104.1 seconds (cold switch) to 32.6 seconds (prefetch-assisted switch), hiding 68.7\% of model loading latency.

The mechanism operates as follows: when the current model group begins execution, the scheduler triggers an asynchronous \texttt{prefetch\_to\_cpu} call that loads the weights of the next model into pinned CPU memory via the gRPC \texttt{LoadModelAsync} endpoint of sllm-store. sllm-store uses \texttt{cudaHostRegister} to allocate a pinned memory pool at startup; the prefetch call loads checkpoint files from SSD into this pool using multi-threaded I/O, making the weights DMA-ready for fast GPU transfer \citep{cuda_guide2024}. This operation runs in a background thread (via \texttt{run\_in\_executor}) while the current group's tasks execute on the GPU. When the model transition occurs, the weights are already resident in pinned memory, enabling direct DMA transfer to GPU at near-peak PCIe bandwidth ($\sim$25\,GB/s), reducing load time from a full disk-to-GPU path ($\sim$100s) to a fast pinned-memory-to-GPU transfer ($\sim$30s).

The residual 32.6 seconds per transition represents the time for GPU memory allocation and weight transfer from CPU to GPU, which cannot be overlapped with computation as it requires the GPU. This sets a lower bound on transition time regardless of prefetching.

The effectiveness of prefetching depends on the overlap window---the elapsed time between the prefetch trigger and the end of the current group. With 30 tasks per group at $\sim$5 seconds each, the full compute time is approximately 150 seconds, which is more than sufficient to complete the CPU prefetch for an 8B model. More generally, for a model with SSD read time $a_i$ and per-task inference time $t$, full prefetch overlap requires at least $\lceil a_i / t \rceil$ tasks in the preceding group. For an 8B model ($a_i = 5.1$s from single NVMe at 3\,GB/s), a group of $\geq$11 tasks at 0.5s each provides sufficient compute time (5.5s) to fully hide the prefetch. For a 32B model ($a_i \approx 20$s), approximately 40 tasks per group are needed --- a requirement easily met in production batch workloads but potentially tight for small batches.

Hypothesis H2 is therefore confirmed: prefetching hides 68.7\% of model loading latency, surpassing the 50\% threshold. The residual 31.3\% is an irreducible lower bound from GPU-side transfer, which cannot be overlapped with computation.

\section{Experiment 4: Johnson's Rule Ordering Ablation}

This experiment validates the effectiveness of Johnson's Rule for ordering model groups by comparing it against naive ordering strategies.

\subsection{Motivation}

Experiments~1--2 demonstrate that model grouping and prefetching dramatically reduce makespan, but do not isolate the contribution of Johnson's Rule ordering. The four-strategy ablation in Experiment~1 demonstrates the aggregate benefit of Johnson's Rule (21\% improvement from Grouping+Prefetch to Shared-Aware), but does not isolate the effect of group ordering from the choice of model count. To validate Johnson's Rule specifically, a controlled experiment is needed with 3+ models having diverse I/O-compute ratios, where all $3! = 6$ orderings can be exhaustively enumerated and compared against the flow-shop model predictions.

\subsection{Methodology}

A 90-task batch was constructed with three models of substantially different sizes:
\begin{itemize}
\item \textbf{Qwen3-0.6B}: 30 tasks, fast load ($a_1 = 0.4$s), fast inference ($b_1 = 9.0$s, $\sim$0.3s/task)
\item \textbf{Qwen3-8B}: 30 tasks, medium load ($a_2 = 5.1$s), medium inference ($b_2 = 15.0$s, $\sim$0.5s/task)
\item \textbf{Qwen2.5-32B-Instruct}: 30 tasks, slow load ($a_3 = 21.7$s), slow inference ($b_3 = 36.0$s, $\sim$1.2s/task)
\end{itemize}

Load times are calculated as $\text{checkpoint\_size} / \text{SSD\_bandwidth}$ (e.g., 15.4\,GB / 3\,GB/s = 5.1\,s for the 8B model). Since there are only $3! = 6$ possible orderings, all are exhaustively evaluated:
\begin{enumerate}
\item \textbf{Johnson's Rule}: 0.6B → 8B → 32B (two-machine flow-shop optimal, Section~\ref{sec:johnsons_rule})
\item \textbf{Alphabetical (model name)}: 32B → 0.6B → 8B (lexicographic sort by full model name\footnote{``Qwen2.5-32B'' $<$ ``Qwen3-0.6B'' $<$ ``Qwen3-8B'' lexicographically.})
\item \textbf{Size-Descending}: 32B → 8B → 0.6B (largest model first, coincides with Total-Time-First)
\item All remaining permutations
\end{enumerate}

All strategies use checkpoint prefetching with eager triggering (prefetch begins at the start of each group). Total makespan and per-group transition times were measured.

\subsection{Analysis}

Johnson's Rule achieves the best measured makespan of 68.3 seconds, outperforming all five alternative orderings. The two-machine flow-shop model predicts these values with a mean error of 1.9\% (Table~\ref{tab:exp4_ordering_results}, Predicted column), confirming that the flow-shop abstraction accurately captures the prefetch-pipeline dynamics of checkpoint scheduling.

Applying the $S_1$/$S_2$ partition from Section~\ref{sec:johnsons_rule}: 0.6B has $a_1=0.4$s, $b_1=9$s ($a \leq b$, enters $S_1$); 8B has $a_2=5.1$s, $b_2=15$s ($a \leq b$, enters $S_1$); 32B has $a_3=21.7$s, $b_3=36$s ($a \leq b$, enters $S_1$). All three groups are compute-heavy, so $S_1$ is sorted by $a_i$ ascending: 0.6B (0.4s) $\to$ 8B (5.1s) $\to$ 32B (21.7s). This ordering minimises the initial I/O cost and maximises the overlap window for each subsequent prefetch.

Both orderings that place 32B first (\#5 and \#6 in Table~\ref{tab:exp4_ordering_results}) incur 21.7 seconds of unmasked GPU-idle time at the start, since no preceding group exists to provide a prefetch overlap window. The subsequent groups (8B and 0.6B) have relatively short I/O times (5.1s and 0.4s) that are trivially hidden by the long 32B compute (36s), but the initial penalty is irrecoverable. The default alphabetical ordering by model name (``Qwen2.5-32B'' $<$ ``Qwen3-0.6B'' $<$ ``Qwen3-8B'') places the I/O-heaviest model first, yielding the worst-case makespan (83.1s). Alphabetical sorting is the natural default for systems that group tasks by model name; Johnson's Rule provides a 21.8\% improvement over this default with no hyperparameter tuning.

Johnson's Rule optimality is theoretically conditioned on deterministic processing times. In practice, LLM output length varies, making $b_i$ estimates uncertain. For this workload, however, all model groups satisfy $a_i \ll b_i$: even the smallest group has $a_1/b_1 = 0.4/9 = 0.04$. Because all groups fall into $S_1$ of Johnson's partition, the optimal ordering reduces to ascending $a_i$ only---a fully deterministic quantity equal to $\text{checkpoint\_size} / \text{bandwidth}$, which does not depend on inference time estimates at all. Inference time uncertainty therefore has zero effect on the JR ordering for compute-heavy LLM workloads. The edge case ($a_i > b_i$, meaning a model group has too few tasks to cover its own load time) is handled by a minimum group-size guard in the implementation; in such cases, the group is placed last to avoid penalising the remainder of the schedule.

Hypothesis H3 is therefore confirmed: Johnson's Rule achieves the best measured makespan (68.3s) and outperforms all naive orderings by 7.2--22.0\%, with the default alphabetical ordering losing 21.8\%. The benefit is deterministic and robust to inference time uncertainty because the JR ordering for compute-heavy workloads depends only on checkpoint size.

\section{Experiment 5: Storage Tier Impact on Prefetching}

This experiment evaluates how different storage tiers affect checkpoint prefetching performance, simulating production scenarios where models must be retrieved from remote repositories rather than local SSD.

\subsection{Motivation}

Production LLM deployments rarely have all models cached locally. Models may reside on remote object storage (S3, GCS) or network file systems (NFS), particularly when the model catalogue exceeds local SSD capacity. Local SSDs, while fast, lack built-in replication; a disk failure can render checkpoints unavailable until they are re-downloaded. Understanding the performance impact of different storage tiers on prefetching effectiveness is therefore essential for production capacity planning.

\subsection{Methodology}

We benchmark model loading time for an 8B model ($\sim$15.4\,GB checkpoint) across four storage configurations:
\begin{itemize}
\item \textbf{Single NVMe SSD}: Local SSD, 3\,GB/s sequential read
\item \textbf{RAID-0 (4× NVMe)}: Striped local SSDs, 12\,GB/s aggregate
\item \textbf{10\,GbE Network (NFS)}: Network-attached storage, $\sim$1.2\,GB/s throughput
\item \textbf{100\,GbE Network (NFS)}: High-speed network storage, $\sim$12\,GB/s throughput
\end{itemize}

The single NVMe SSD configuration is directly measured on the cluster hardware. The RAID-0, 10\,GbE NFS, and 100\,GbE NFS configurations are analytically computed as $\text{checkpoint\_size} / \text{bandwidth}$ using published hardware specifications and validated against sllm-store benchmark results; these configurations were not physically available on the test cluster. For each tier, we report: (1) SSD-to-RAM or network-to-RAM transfer time, (2) pinned-RAM-to-GPU transfer time (PCIe DMA, constant across tiers), and (3) end-to-end model loading time. We then calculate the minimum overlap window required for checkpoint prefetching to fully hide the I/O latency. A 60-task batch with 2 models (30 tasks each) is used for the NVMe end-to-end makespan measurement; other tiers report analytical estimates.

\subsection{Analysis}

For high-bandwidth tiers (RAID-0, 100\,GbE), loading time is already short ($\sim$2\,s), leaving minimal room for prefetching to reduce (3.7--4.0\% reduction). The largest absolute benefit arises for 10\,GbE NFS (12.8s read time), where prefetching saves 10.1\,s (23.1\% reduction), making prefetching most valuable at mid-bandwidth.

Regardless of storage tier, the GPU memory transfer (0.9\,s via PCIe Gen4 x16) is irreducible, so the pure I/O component of a model transition cannot be shorter than $\sim$1\,s (Figure~\ref{fig:exp5_storage_tier}a). This I/O lower bound is distinct from the practical transition lower bound: Experiment~2 measures a 32.6\,s residual after prefetching, which includes GPU memory allocation and vLLM engine initialisation ($\sim$32\,s) that cannot be overlapped with computation regardless of storage tier. Experiment~5 isolates the I/O component only; the vLLM initialisation overhead is constant across all storage tiers.

While 10\,GbE NFS adds 7.7s of read latency relative to single NVMe, it provides critical fault tolerance through built-in replication. Prefetching compensates for most of this additional latency (78.9\% hidden), reducing the practical penalty to 2.7s of residual wait---an acceptable trade-off for the capacity and replication benefits of remote storage.


\section{Evaluation Summary}

The three optimisations are complementary and compose multiplicatively: model grouping provides first-order benefit (99\% makespan reduction, 71$\times$ speedup), checkpoint prefetching provides second-order benefit (additional 1.6$\times$, hiding 68.7\% of total cold-switch latency on local SSD, Experiment~2; hiding 78.9\% of the I/O read time on 10\,GbE NFS, Experiment~5), and Johnson's Rule provides third-order benefit (additional 1.2$\times$, 7.2--22.0\% over naive orderings). For a production workload with 10,000 tasks across 5 models, the combined effect transforms an 18-day FIFO execution into a 2-hour batch completion (237$\times$ speedup).

Compared to industrial batch APIs (OpenAI Batch, AWS Bedrock), our system's key advantage is multi-model batch support with shared-structure-aware scheduling. Industrial systems are single-model only and do not expose scheduling policies, though they offer superior scale and reliability.

\section{Summary}

The experimental evaluation demonstrates three levels of compounding optimisation. Model grouping provides first-order benefit (99\% makespan reduction over FIFO, 71$\times$ speedup), checkpoint prefetching provides second-order benefit (hiding 68.7\% of total cold-switch latency on local SSD, Experiment~2; hiding 78.9\% of the I/O read time on 10\,GbE NFS, Experiment~5), and Johnson's Rule ordering provides third-order benefit (7.2--22.0\% improvement over naive orderings, robust to inference time uncertainty). The shared-aware strategy outperforms FIFO by 49--237$\times$ across production batch sizes of 100--10,000 tasks, with advantages growing towards an asymptotic limit of 247$\times$. The system remains effective with network-attached replicated storage, making it viable for production deployments where fault tolerance is critical.

\chapter{Discussion}

This chapter interprets the experimental findings, answers the research questions posed in Chapter~1, and discusses limitations.

\section{Answering the Research Questions}

\paragraph{RQ1: How to Discover and Exploit Shared Structure?}

Model grouping effectively discovers and exploits the dominant shared structure in batch workloads: shared model weights. Grouping reduces switches from $O(n)$ to $O(k)$, yielding a 99\% makespan reduction (Experiment~1). The shared-aware strategy outperforms all baselines across batch sizes 100--10,000 and model sizes 0.6B--32B (Experiment~3), with advantages growing as batch size increases because larger batches amortise the fixed model loading cost over more tasks.

\paragraph{RQ2: Can the Problem Be Modelled as a Two-Machine Flow-Shop?}

Yes. The batch scheduling problem maps naturally to a two-machine flow-shop where Machine~A is I/O (loading model weights) and Machine~B is GPU computation. Johnson's Rule determines the optimal model group ordering to maximise overlap between loading and execution. Checkpoint prefetching implements this overlap, hiding 68.7\% of model loading latency (Experiment~2). Experiment~4 validates that Johnson's Rule outperforms naive orderings by 7.2--22.0\%, with the largest gains occurring when the default alphabetical ordering happens to place I/O-heavy models first. The combination of Johnson's Rule ordering with prefetching is more effective than naive ordering because compute-heavy groups are scheduled first, providing a longer overlap window for prefetching the next model.

\paragraph{RQ3: How Do Strategies Compare?}

FIFO is unsuitable for multi-model batches due to excessive switching (96\% of time spent on loading). Model Grouping provides deterministic first-order improvement by eliminating redundant switches. Shared-Aware (grouping + Johnson's Rule + prefetching) provides additional benefit through I/O-computation overlap. The relative advantage is consistent across model sizes 0.6B--32B (Experiment~3), indicating robustness. Johnson's Rule provides measurable benefit (7.2--22.0\%) when the batch contains models with diverse I/O-compute characteristics (Experiment~4). Model grouping with Johnson's Rule ordering should be the default for any multi-model batch workload.

\section{What Was Built vs What Was Reused}

The division of labour between existing infrastructure and new contributions is clarified below.

The ServerlessLLM framework ($\sim$15K LoC Python + C++) provides the API gateway, router, SQLite database, sllm-store checkpoint manager (C++ with gRPC interface), Pylet worker process, autoscaler, and reconciler. The vLLM inference engine handles all GPU-level computation (attention kernels, KV cache management, continuous batching). Model checkpoints were downloaded from HuggingFace.

New contributions include the \texttt{BatchScheduler} class (\texttt{sllm/batch\_scheduler.py}, $\sim$1,400 lines), which implements model grouping with task sorting, Johnson's Rule ordering via the $S_1$/$S_2$ partition algorithm, checkpoint prefetch triggering with a memory-aware guard, semaphore-based admission control, multi-GPU group assignment using greedy LPT with rebalancing, automatic tensor parallelism detection, and deployment lifecycle management (deploy/undeploy sequencing with nvidia-smi polling for GPU memory release). The batch REST API (\texttt{api\_gateway.py}) follows the OpenAI Batch API specification (\texttt{POST /v1/files}, \texttt{POST /v1/batches}, \texttt{GET /v1/batches/\{id\}}) extended to support multi-model batches. The \texttt{StorageManager} was extended with prefetch integration for the sllm-store pinned memory pool. All experiment benchmark scripts ($\sim$1,400 lines across 7 scripts), plotting and parameter configuration utilities (\texttt{plot\_results.py}, \texttt{mock\_params.py}), and unit tests ($\sim$800 lines, 48 tests) were written from scratch, totalling approximately 3,500 lines of new Python code.

Database schema extensions for batch jobs and tasks, FastAPI endpoint wiring, and experiment harness setup were straightforward integration work. Three aspects required substantial debugging effort: prefetch integration with sllm-store's pinned memory pool, where understanding the C++ gRPC interface and \texttt{cudaHostAlloc} semantics was necessary to prevent conflicts between prefetched and currently-loaded models; GPU memory release during model transitions, since vLLM retains CUDA context after logical cancellation and nvidia-smi polling was required to confirm memory was freed before launching the next model; and obtaining reliable measurements on a shared GPU cluster where other users' workloads introduced I/O variability.

\section{Design Trade-offs}

Several design decisions warrant explicit justification.

Experiment~1 shows that any model-aware strategy dramatically outperforms synchronous FIFO (575s vs 78,900s for 500 tasks), justifying the semaphore concurrency approach despite its added complexity. The semaphore buffer size (default 10) controls the trade-off between GPU utilisation (higher buffer) and memory pressure (lower buffer).

Model grouping (Phase~1) and Johnson's Rule ordering (Phase~2) are independent and composable: grouping provides the dominant benefit, and Johnson's Rule adds an additional 7--22\% on top. This separation allows deploying grouping alone when the I/O-time estimates required by Johnson's Rule are unreliable (e.g., under variable network bandwidth).

Operating above the inference engine at the cluster-scheduler level ensures portability across vLLM, SGLang, and TensorRT-LLM without engine modifications. The cost is that engine-level optimisations (e.g., prefix caching across model groups) cannot be directly exploited by the scheduler.

\section{Algorithm Limitations}

Four limitations warrant discussion. First, the single-model-per-worker assumption is suboptimal for LoRA adapters, which can share base models with sub-second swaps. Second, Johnson's Rule assumes deterministic processing times, but LLM inference times vary with output length; conservative estimates based on model size are used instead. Third, the memory-aware prefetch guard is conservative---it skips prefetching when CPU pinned memory is tight rather than evicting cached models. Fourth, the algorithm processes one batch at a time without multi-tenant fairness guarantees.

Johnson's Rule delivers maximum benefit when models have strongly contrasting I/O-compute ratios. When all models have similar ratios (e.g., all small models or all large models), any permutation yields nearly identical makespan and Johnson's Rule provides no benefit over alphabetical ordering. In the degenerate case where $a_i = b_i$ for all groups, the rule reduces to arbitrary ordering. The scheduler correctly handles this boundary condition (Johnson's Rule still runs, it just happens to match FIFO), but users should not expect significant gains from a homogeneous model catalogue.

The theoretical makespan lower bound for the two-machine flow-shop is:
$$C_{\max}^* \geq \max\left(\sum_{i=1}^k b_i,\; \min_i a_i + \sum_{i=1}^k b_i,\; \sum_{i=1}^k a_i + \min_i b_i\right)$$
For our Exp~4 workload ($\sum b_i = 9+15+36 = 60$s, $\min a_i = 0.4$s), the lower bound is $\max(60, 60.4) = 60.4$s. Johnson's Rule achieves 67.1s, within 11.1\% of this theoretical optimum. The gap arises because the 32B model's 21.7s load cannot be fully overlapped with the 8B group's 15s compute, leaving a 6.7s residual. This illustrates that while Johnson's Rule is optimal among all orderings, the absolute makespan depends on the I/O:compute balance of the workload.

\section{Threats to Validity}

\paragraph{Internal Validity}
Experiments were conducted on a shared GPU cluster; other users' GPU processes and I/O could affect timing measurements. Experiments 1 (strategy comparison), 3 (scalability), and 4 (ordering ablation) report measurements from a live ServerlessLLM cluster with cold-start verification between runs. Each data point is the mean of 3 independent runs; we report $\pm 1$ standard deviation.

The prefetch and Johnson's Rule experiments (Experiments 2 and~4) require models with diverse checkpoint sizes (0.6B, 8B, 32B) to produce meaningful transition cost variation. With only small, similarly-sized models on fast NVMe SSD, both prefetch overlap and group ordering have limited effect because the I/O cost per transition is small relative to compute time. The benefit of these optimisations scales with the number and size diversity of models in the batch. Experiment~3 demonstrates this scaling up to 10,000 tasks; production workloads with 8+ models spanning a wider parameter range (1B--70B) would approach the 247$\times$ asymptotic limit more quickly due to larger per-switch overheads.

\paragraph{External Validity}
We evaluated five Qwen models (0.6B--32B) on a single hardware configuration (RTX A5000, NVMe SSD). Results may not generalise to mixture-of-experts architectures, different storage technologies (e.g., Lustre, CephFS), or larger clusters. The model switching overhead is hardware-specific; faster storage would reduce the absolute benefit of model grouping, though the relative advantage remains consistent.

\paragraph{Construct Validity}
Makespan ($C_{\max}$) does not capture per-task latency distribution, resource cost, or fairness. A multi-objective evaluation would be more appropriate for production deployments. Additionally, our flow-shop model assumes no preemption and fixed group sizes; relaxing these assumptions would require more general scheduling theory (e.g., open-shop or flexible flow-shop).

\chapter{Future Work}
\label{ch:future}

This chapter outlines three directions for extending the shared-aware scheduling system.

\section{Inference-Level Extensions: Prefix-Aware Ordering and Multi-LoRA}

The current system groups tasks by model but does not exploit prompt prefix sharing. Extending the scheduler to sort tasks within each model group by prefix hash would maximise inference engine cache reuse (e.g., RadixAttention in SGLang), with the key challenge being efficient prefix detection without full prompt comparison. Additionally, the system currently treats each LoRA adapter as a separate model; since multiple adapters can share a base model with sub-second swaps ($<$1s vs 80--120s full reload), grouping by base model and exploiting multi-LoRA serving in vLLM \citep{sheng2024slora} would provide significant speedup for adapter-heavy workloads.

\section{Storage Extensions: Adaptive and Network-Aware Prefetching}

The current prefetching mechanism triggers at a fixed point (the start of each group). An adaptive policy would observe task completion times in real time and adjust the trigger point dynamically, maximising I/O-computation overlap for heterogeneous task groups. For network storage, integrating with cloud object storage APIs (S3, GCS, Azure Blob) and using bandwidth-aware scheduling that dynamically adjusts prefetch timing based on observed network throughput would enable direct streaming from replicated storage without local caching. Experiment~5 demonstrates that the architecture already supports network storage effectively; the remaining work is engineering rather than algorithmic.

\section{Production Readiness: Scalability and Engine Abstraction}

Three engineering improvements would enable production-scale deployment: output file aggregation via streaming JSONL writes to object storage, deadline-aware autoscaling ($\text{workers} = \lceil n \cdot L_{avg} / T_{deadline} \rceil$), and multi-node data parallelism with distributed task queues. The current system is coupled to vLLM; abstracting the inference engine interface would enable support for SGLang \citep{zheng2024sglang}, TensorRT-LLM \citep{tensorrt_llm2024}, and other backends. The multi-GPU scheduling algorithm (Section~4.5) is implemented but requires experimental validation on multi-GPU configurations to confirm the greedy LPT assignment achieves balanced load in practice.

\chapter{Conclusion}

This dissertation addressed makespan minimisation for LLM batch inference by discovering and exploiting shared structure in batch tasks. The problem was formalised as a two-machine flow-shop, and a shared-aware scheduling algorithm was proposed that applies Johnson's Rule at the cluster scheduler level without modifying the inference engine.

\section{Contributions}

Five contributions are made: (1) a two-machine flow-shop formulation mapping model loading (I/O) and GPU inference (compute) to Johnson's classical framework; (2) a shared-aware scheduling algorithm that groups tasks by model and applies Johnson's Rule for optimal group ordering; (3) a checkpoint prefetching mechanism that preloads model weights via the pinned memory pool of sllm-store during computation; (4) design analysis and evaluation of prefetching across storage tiers (SSD, RAID, NFS); and (5) an OpenAI-compatible batch API extended for multi-model batches.

\section{Key Findings}

Model switching is the dominant bottleneck for multi-model batches, with an average per-switch overhead of $\sim$157\,s across a five-model workload. Model grouping reduces makespan by 99\% (78,900s $\to$ 1,107s for a 500-task batch), eliminating $O(n)$ switches. Checkpoint prefetching provides an additional 1.6$\times$ improvement; Johnson's Rule ordering adds a further 1.2$\times$, for a combined 137$\times$ speedup over FIFO. The shared-aware strategy outperforms FIFO by 49--237$\times$ across batch sizes of 100--10,000 tasks, with advantages growing as $n$ increases towards the asymptotic limit of $247\times$. Across model sizes (0.6B--32B), consistent 5.3--6.8$\times$ speedup confirms robustness. Checkpoint prefetching hides 68.7\% of total cold-switch latency on local SSD (Experiment~2, measuring full transition time including vLLM initialisation) and 78.9\% of the I/O read time on 10\,GbE network storage (Experiment~5, isolating the I/O component). Johnson's Rule provides an additional 7.2--22.0\% makespan reduction over naive orderings and is robust to inference time estimation uncertainty.

The central insight is that batch tasks are not independent: they contain exploitable shared structure that the scheduler should discover and leverage. The algorithm is general and portable---it operates above the inference engine, making it applicable to vLLM, SGLang, TensorRT-LLM, and other backends without modification. The OpenAI-compatible batch API enables migration from cloud services to self-hosted infrastructure without client code changes. By demonstrating that simple scheduler-level optimisations can dramatically reduce makespan even with network-attached storage, this work provides a foundation for batch-optimised LLM serving systems.
