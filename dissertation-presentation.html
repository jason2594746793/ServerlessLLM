Efficient Scheduling for Batched AI Jobs

Minimising Makespan through Model Grouping, Johnson's Rule, and Checkpoint Prefetching

Jingsheng Chen
1

Why Batch LLM Inference?

  • Enterprises run thousands of offline tasks daily: summarisation, classification, extraction
  • Researchers submit large-scale benchmarks across multiple models for evaluation suites, leaderboard runs, and ablation studies
  • Real-time latency is not required; throughput and cost matter most
  • model loading is expensive: switching a 7–8B model costs ~5–15s on NVMe SSD; at O(N) switches this dominates makespan

Core question: given a batch of offline LLM tasks submitted before execution begins, how can the scheduler exploit shared structure to minimise total completion time (makespan)?

Research Questions & Contributions

  1. RQ1: How much makespan can model grouping and checkpoint prefetching save compared to naive FIFO scheduling?
  2. RQ2: Can classical flow-shop theory (Johnson's Rule) improve the model execution order for I/O-compute overlap?
  3. RQ3: How should work be distributed across multiple GPUs to minimise the longest-running device?

Scheduling Techniques

  • Model-grouped scheduling, reduces switches from O(N) to O(K)
  • Aggressive checkpoint prefetch, overlaps SSD-to-CPU I/O with GPU compute
  • Memory-aware prefetch guard, skips prefetch when CPU pinned memory is full

System Design

  • Greedy worker assignment, assigns model groups to GPUs by least-load balancing
  • Johnson's Rule ordering, optimal group sequence for two-machine flow-shop overlap
  • Three concurrency strategies (sync, chunked, semaphore)
5

Related Work

LLM Serving & Scheduling

  • Batch inference at scale: OpenAI Batch API, AWS Bedrock batch mode treat tasks as fire-and-forget jobs, but use simple FIFO queues internally
  • Model-aware serving: vLLM, ServerlessLLM, Orca optimise single-request latency and memory; none schedule across a batch of heterogeneous tasks
  • Classical scheduling: FIFO, SJF, Fair Share are task-level; they ignore the shared structure (model weights) between tasks

Prefetching & Pipelining

  • Checkpoint loading: sllm-store provides fast SSD-to-GPU transfer via pinned memory, but the scheduler does not coordinate prefetch timing
  • Layer-wise prefetch: DeepSpeed, FlexGen overlap layer transfers with compute within a single model; no cross-model prefetch at the scheduler level
  • Flow-shop theory: Johnson's Rule (1954) solves two-machine makespan optimally, but has not been applied to model-switch I/O overlap

Gap: fast checkpoint loading exists, batch APIs exist, but no scheduler exploits shared model structure across a batch to minimise makespan.

Concurrency Strategies

Three strategies control how tasks within a model group are dispatched to the Router:

sync

Sequential

One task at a time. Simplest, lowest throughput. Useful as a baseline.

chunked

Fixed Chunks

Submit buffer_limit tasks, wait for all to finish, repeat. Bursty but predictable.

semaphore · default

Sliding Window

Maintain up to buffer_limit in-flight tasks. As one completes, the next fires immediately. Maximises GPU utilisation.

Johnson's Algorithm

Ordering K model groups to minimise prefetch makespan is a 2-machine flow-shop (SSD → GPU). Johnson (1954) gives a provably optimal O(K log K) algorithm:

Input: K groups, each with load time pᵢ (SSD→GPU) and compute time qᵢ (GPU)

1.  Partition:  S₁ = { i : qᵢ ≥ pᵢ }  ·  S₂ = { i : qᵢ < pᵢ }

2.  Sort S₁ by ascending pᵢ  (shortest load first)

3.  Sort S₂ by descending qᵢ (longest compute last)

4.  Schedule: S₁ then S₂

S₁ (compute ≥ load, ascending load):

Qwen3-0.6B (1.2 GB) → Qwen2.5-7B (14.3 GB)

S₂ (load > compute, descending compute):

Qwen3-8B (15.4 GB) — placed last

At 3 GB/s NVMe all groups are compute-heavy, so the algorithm degenerates to smallest checkpoint first.

S₁ jobs (small load, ample compute) go first so their long GPU phase fully covers the next model's SSD prefetch. S₂ jobs (large load relative to compute) go last in descending compute order to maximise partial overlap. The algorithm is provably optimal for the 2-machine flow-shop.

Extending to 3-Machine Flow-Shop

When checkpoints live on network/internet storage, each model group traverses three machines in sequence:

Reduction to 2-Machine

Define virtual times combining adjacent machines:

aᵢ = dᵢ + pᵢ   (network + SSD load)

bᵢ = pᵢ + qᵢ   (SSD load + compute)

Apply Johnson's Algorithm to (aᵢ, bᵢ)

Valid when M₂ (SSD) is never the bottleneck: min(dᵢ) ≥ max(pᵢ) or min(qᵢ) ≥ max(pᵢ)

Practical Implication

  • Typical lab / cloud (1–10 GbE, ~125 MB/s–1.25 GB/s): SSD load (∼1–13 GB/s) exceeds download — condition holds, reduction is valid
  • Ultra-fast lab (25 GbE, ~3.1 GB/s): may exceed SATA RAID SSD (∼1.5 GB/s); condition can fail — reduction becomes a heuristic, not guaranteed optimal
  • Data-centre backbone (100 GbE, ~12.5 GB/s): only NVMe RAID (∼13 GB/s) can keep up; direct Internet→CPU streaming may be faster than SSD caching
  • When condition fails, optimal 3-machine scheduling is NP-hard; the reduction gives a practical approximation

The reduction is exact when internet < SSD (most labs and cloud deployments today). As network speeds approach or exceed SSD bandwidth, the 3-machine problem becomes intractable — making faster local storage (NVMe RAID, ∼13 GB/s) or direct streaming with parallel SSD write the right architectural response.

Limitations & Future Work

Current Limitations

  • When pinned memory is limited, the optimal arrangement becomes NP-hard.
  • Offline batch only, no mixed online/offline priority

Future Directions

  • Multi-tenant extension: global task pool merging across users with fairness guarantees
  • Live memory telemetry: Grouping tasks with similar prefixes to allow higher KV-cache hit rates
  • Hybrid scheduling: mix real-time and batch with priority preemption
17

Conclusion

  • Model grouping reduces switches from O(N) to O(K), eliminating redundant checkpoint loads — dominant win for heterogeneous batches
  • Checkpoint prefetch overlaps SSD→CPU I/O with GPU compute via flow-shop pipelining, hiding model-switch latency between groups
  • Johnson's Rule orders groups to maximise I/O-compute overlap, provably optimal for the two-machine flow-shop formulation
  • Multi-GPU assignment with greedy LPT balances model groups across 8× RTX A5000 GPUs, enabling near-linear throughput scaling

Together, these techniques make serverless batch LLM inference practical: model-switch overhead drops from a dominant cost to a marginal one, enabling high-throughput offline workloads on commodity GPU clusters.
